# NamiShelf — Service Integration and Feature Orchestration

**Status:** Proposed integration architecture; provider and API details remain subject to M0 and subsystem reviews.

## 1. Purpose

Define how NamiShelf's major capabilities compose without allowing UI features, extensions, providers or external services to bypass domain ownership and security boundaries.

## 2. Source and extension request path

Expected request path:

    Browse / Reader / Library
       → Application use case
       → Source service
       → Extension broker (when source is extension-backed)
       → Per-extension child process
       → Origin-restricted network gateway
       → Remote source

The source service owns source identity, source capabilities and request orchestration. The broker owns extension authorization, request validation, quotas, origin policy and stream handles. Extensions never receive direct database connections, global credentials or unrestricted host filesystem access.

Built-in sources, if any, should use the same source-facing domain contract but may use trusted in-process adapters. Do not give built-in and third-party sources divergent semantics without a documented reason.

## 3. Reader and image pipeline

Reader flow:
1. Resolve library entry and chapter through domain repositories.
2. Obtain chapter page descriptors through the source service.
3. Fetch pages through an authorized source/network path.
4. Stream bytes through bounded handles or managed temporary storage.
5. Validate media type, size and decode limits.
6. Decode via the desktop image pipeline with memory reservations.
7. Present pages and release resources deterministically when pages leave the active window.

Reader must prioritize stability and bounded memory. Prefetch is adaptive and subordinate to memory budgets measured on the Mint reference device. Failed or unsupported image formats produce explicit page errors; do not silently skip pages.

## 4. Downloads

A download use case creates a durable job and a managed artifact manifest. The scheduler owns concurrency, retries, pause/resume, integrity checks and disk-space handling. Filesystem paths are generated by NamiShelf storage policy, not accepted verbatim from extensions.

A download is complete only when all expected pages/artifacts pass validation and the manifest is committed. Interrupted downloads resume only when source identity and validators make resumption safe. Cache eviction must not remove completed downloads.

## 5. Tracking

Tracker adapters implement a common tracker contract. Credentials are stored in the OS credential service and injected only into the tracker adapter that needs them. Tracking associations are local user data. Release-1 sync scope excludes tracking associations; ordinary backup may include portable association metadata but never tracker tokens/passwords.

Tracking failures must not block library or reader operations.

## 6. Backup orchestration

Backup service requests a consistent domain snapshot from the owning repositories, serializes it through the NamiShelf native adapter or Mihon legacy adapter, and writes through a user-selected destination. Restore first parses and validates into a staging model, presents a preview and only then applies through domain use cases in a recoverable transaction.

Do not back up raw database files as the canonical interchange format. Do not auto-enable imported source repositories or extensions.

## 7. Synchronization orchestration

Sync service observes only the release-1 sync-eligible core entities: library entries, chapter read/progress state, categories and followed authors. Domain mutations produce journal operations; the sync engine encrypts them before provider adapter calls.

Provider adapters cannot inspect plaintext payloads or make domain merge decisions. Sync is background, cancellable and offline-tolerant. Tracking, history, downloads, extension state and credentials are excluded from release-1 sync.

## 8. Extension lifecycle

Extension manager owns:
- repository/artifact provenance and digest verification;
- installation transaction and rollback;
- compatibility profile validation;
- user permission/profile assignment;
- child-process start/handshake/health/shutdown;
- capability revocation and process termination;
- crash isolation and bounded diagnostics.

Installing an extension does not imply enabling it. Restoring extension repository metadata does not execute or trust an artifact.

## 9. Background task orchestration

Downloads, backup, sync and extension lifecycle are long-running operations with:
- stable operation ID;
- explicit state machine;
- progress units and cancellation;
- retry classification;
- durable checkpoint where appropriate;
- user-visible error and recovery action;
- redacted diagnostics.

Avoid one global scheduler that owns unrelated policies. A shared task/status surface may aggregate state, while each subsystem retains its own execution policy.

## 10. Integration contracts and failure isolation

- Source outage does not block other sources.
- Tracker outage does not block reading.
- Sync outage does not block local library operations.
- Extension crash does not crash the host or another extension.
- Backup failure must not corrupt the active profile.
- Reader decode failure is isolated to the affected page/session.
- Credential-store failure blocks secret-dependent operations without plaintext fallback.

## 11. Open technical details

- Exact source API adapter and Android/Mihon shim coverage.
- HTTP client ownership and cookie partitioning.
- Download scheduler implementation and file manifest.
- Tracker adapter contract and credential injection.
- Database snapshot/transaction strategy for backup.
- Background task persistence and restart recovery.
- Process supervisor implementation across package formats.

No integration code or runtime test has been performed.
